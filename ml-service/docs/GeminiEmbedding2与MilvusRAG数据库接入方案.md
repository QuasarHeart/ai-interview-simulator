# Gemini Embedding 2 与 Milvus 的 RAG 数据库接入方案

> 文档定位：面向人工智能面试模拟器的知识底座设计说明，重点介绍如何基于 Gemini Embedding 2 与 Milvus 构建一个可扩展、可治理、可追踪的 RAG 数据库与检索体系。
>
> 文档目标：不讨论具体代码实现，只讨论架构、数据组织、索引设计、检索策略、岗位适配与运营治理。

## 1. 方案总览

本方案的核心目标，不是简单把资料“塞进向量库”，而是建立一套面向面试场景的知识检索中枢。这个中枢既要能理解岗位差异，又要能识别问题意图，还要能把语义检索、关键词检索、元数据过滤和结果重排统一到同一条链路中。

在这个体系里，text-embedding-v4 负责把文本、制度、案例、岗位材料、题库、面试复盘等内容映射到统一向量空间；Milvus 负责承载大规模向量存储、相似度检索、分区隔离、元数据过滤和混合召回；上层检索编排器负责理解问题、路由岗位、选择召回策略，并把最终证据交给大模型生成答案或建议。

这个方案适合以下场景：

- 面试官问答辅助，快速找出与岗位相关的知识证据。
- 面试题生成，基于岗位知识图谱召回合适素材。
- 回答解释与追问建议，基于上下文做证据增强。
- 跨岗位知识共享，既能命中通用能力，也能命中特定岗位技能。
- 知识版本治理，保证新旧文档、不同模型版本、不同岗位之间互不污染。

## 2. 设计原则

### 2.1 语义优先，但不放弃精确匹配

RAG 的第一目标是“找对内容”，不是“找最像的句子”。因此，语义召回应该作为主通道，但对于框架名、错误码、配置项、命令行参数、API 名称、指标名这类强精确内容，必须保留关键词通道。

### 2.2 岗位优先，而不是全库平铺

十个岗位的知识结构天然不同。数据工程师看的是数据链路，DevOps 看的是交付和运维，系统架构师看的是权衡与约束。检索系统必须先识别岗位，再决定召回范围，而不是把全库文档一视同仁地做相似度搜索。

### 2.3 证据优先，而不是摘要优先

RAG 的价值不是“生成一段看起来合理的话”，而是提供可追溯证据。最终输出应该尽量保留来源、章节路径、版本和片段边界，让回答具备可解释性。

### 2.4 版本优先，而不是静态一次性入库

知识库不是一次构建就结束。模型版本、岗位标准、工具链、技术栈、面试规范都会变化，所以必须内置版本字段、更新时间、失效标记和回滚机制。

### 2.5 召回与生成解耦

检索层负责“找到最有用的证据”，生成层负责“组织成面试可用的表达”。两者职责分离，才能降低幻觉和噪音。

## 3. 知识体系分层

建议把整个知识库分成五层，而不是把所有资料塞进一个平面空间里。

### 3.1 通用能力层

这部分内容不直接绑定某个岗位，而是支撑所有岗位的基础能力判断，包括：

- 面试流程与评价原则。
- 沟通、表达、结构化思考、问题拆解。
- 分布式系统、工程实践、质量意识、可靠性意识。
- 通用算法、数据结构、系统设计方法论。

### 3.2 岗位能力层

每个岗位都应有自己的核心知识层。比如：

- 数据工程师关注数据建模、ETL/ELT、数据质量、调度、湖仓。
- 后端工程师关注接口设计、并发、缓存、消息队列、事务、性能。
- 机器学习工程师关注特征、训练、评估、部署、推理与 RAG。
- DevOps 与 SRE 关注交付、部署、监控、告警、SLO、容量与故障处理。

### 3.3 场景案例层

场景层是 RAG 中最有价值的部分之一。它承载的是“怎么做”的知识，而不是“是什么”的定义。建议包括：

- 系统设计案例。
- 故障复盘案例。
- 性能优化案例。
- 测试策略案例。
- 交付与发布案例。
- 模型训练与上线案例。

### 3.4 评价规则层

这部分内容用于支撑面试判断与追问逻辑，包括：

- 岗位评分维度。
- 常见扣分项。
- 优秀回答特征。
- 面试官追问模板。
- 不同级别候选人的判断标准。

### 3.5 运行治理层

这是最容易被忽略、但最影响长期稳定性的层：

- 文档版本。
- 来源可信度。
- 生效时间。
- 失效时间。
- 安全等级。
- 审计信息。

## 4. 岗位知识图谱设计

本方案针对以下十个岗位建立统一的岗位编码体系：

| 岗位代码 | 中文岗位名 | 核心关注点 |
| --- | --- | --- |
| `data_engineer` | 数据工程师 | 数据建模、ETL/ELT、数据质量、调度、湖仓 |
| `devops` | 开发运维 | CI/CD、容器、Kubernetes、IaC、可观测性 |
| `golang_backend` | 后端工程师（Golang） | 并发、性能、服务治理、网络编程 |
| `java_backend` | 后端工程师（Java） | Spring、JVM、事务、微服务、中间件 |
| `machine_learning_engineer` | 机器学习工程师 | 特征、训练、评估、部署、推理、RAG |
| `python_backend` | 后端工程师（Python） | Web 框架、异步、测试、接口与集成 |
| `site_reliability_engineer` | 网站可靠性工程师 | SLI/SLO、故障处理、容量、稳定性 |
| `software_test_engineer` | 软件测试工程师 | 测试策略、自动化、质量门禁、缺陷管理 |
| `system_architect` | 系统架构师 | 架构权衡、标准化、扩展性、治理 |
| `web_frontend` | Web 前端工程师 | 组件化、性能、体验、可访问性 |

建议把岗位知识图谱再细分成三类边：

- 纵向边：同一岗位内部的知识深度演进，例如从基础概念到高级实践。
- 横向边：跨岗位共享知识，例如后端与 SRE、ML 与数据工程、前端与测试。
- 事件边：面试题、故障复盘、项目案例、版本变更等动态知识。

这种图谱化组织方式，能让检索系统在“同岗位精确命中”和“跨岗位知识迁移”之间保持平衡。

## 5. Gemini Embedding 2 的向量化策略

### 5.1 模型定位

Gemini Embedding 2 适合做统一语义空间的基础编码层。按照 Milvus 官方给出的接入建议，该模型支持默认 3072 维输出，并可按需要选择 768、1536 或 3072 维的输出维度。对于中文、英文以及混合语料，它都能提供稳定的语义表达能力。

### 5.2 维度选择建议

维度不是越大越好，而是要和检索场景匹配。

| 维度 | 适用场景 | 特点 |
| --- | --- | --- |
| 768 | 高并发、成本敏感、快速落地 | 存储压力小，检索成本低，适合首期上线 |
| 1536 | 默认生产推荐 | 性能、成本、召回之间比较均衡 |
| 3072 | 高召回、高精度、核心知识库 | 语义表达更细，适合高价值文档与复杂问题 |

对于这个面试项目，建议采用“分层维度”策略：

- 主检索库使用 1536 维，兼顾效果和成本。
- 核心高价值知识库可使用 3072 维，作为高精度补充层。
- 如果要做高并发、低延迟的轻量级部署，可保留 768 维的快速库。

### 5.3 文档与查询的任务类型

Gemini Embedding 2 支持把不同阶段的输入任务区分开来：

- 文档入库阶段建议使用文档向量化语义，强调“可被检索”。
- 查询阶段建议使用查询向量化语义，强调“问题意图”。

这类任务区分的意义在于：同一条知识在“写入”和“搜索”时的最佳表示方式并不完全相同。把两种任务混在一起，会明显影响召回质量。

### 5.4 输入预处理策略

在送入 Embedding 之前，建议先做以下处理：

- 删除无意义页眉、页脚、版权冗余和模板噪音。
- 保留标题层级、列表层级和章节路径。
- 代码、命令、配置键、错误码、指标名要原样保留。
- 中英文混排内容统一成语义完整的短段落。
- 表格信息尽量转成结构化文本，而不是直接整表压缩。
- 对重复定义、重复说明、空泛口号进行去重。

### 5.5 切分原则

切分不是机械按字符数分块，而是按语义单元分块。

建议采用三段式切分：

1. 先按章节与小节边界切。
2. 再按主题完整性切。
3. 最后在超长段落上做长度兜底切分。

推荐思路是：

- 概念类内容：保持 1 个概念单元完整。
- 流程类内容：保持 1 条流程链完整。
- 案例类内容：保持“背景 - 问题 - 方案 - 结果”完整。
- 代码类内容：保持代码块和解释成对出现。

如果必须给出一个工程范围，建议将单 chunk 控制在“一个主题可以讲清楚”的粒度，而不是追求固定长度。

### 5.6 版本治理

Embedding 模型一旦发生版本变化，就可能改变向量空间，因此必须对版本进行显式治理：

- 每条记录都保留 `embedding_model` 与 `embedding_version`。
- 大版本升级时不要直接覆盖旧向量，优先新建版本集合或版本分区。
- 允许同一文档在不同版本中并存，便于灰度和回滚。

## 6. Milvus 数据库设计

### 6.1 总体结构建议

建议把 Milvus 作为“统一知识检索层”，而不是仅仅当成一个向量容器。推荐的逻辑结构如下：

- 一个主知识库集合承载通用知识与岗位知识。
- 以 `role_code` 作为一级分区或强过滤字段。
- 以 `doc_type`、`source_type`、`version_tag`、`security_level` 等字段做二级过滤。
- 对精确匹配需求高的内容增加稀疏向量或全文检索通道。

### 6.2 推荐字段设计

| 字段名 | 作用 | 说明 |
| --- | --- | --- |
| `doc_id` | 文档主键 | 唯一标识一篇文档或一个知识单元 |
| `chunk_id` | 分块主键 | 唯一标识一个 chunk |
| `role_code` | 岗位编码 | 用于岗位隔离与路由 |
| `role_tags` | 岗位标签 | 支持一条知识对应多个岗位 |
| `doc_type` | 文档类型 | 例如规范、案例、FAQ、runbook、ADR |
| `title` | 标题 | 便于展示和追溯 |
| `section_path` | 章节路径 | 保留来源位置，如“第 3 章 / 3.2 小节” |
| `chunk_text` | 原始文本 | 用于生成上下文与引用 |
| `dense_vector` | 稠密向量 | Gemini Embedding 2 输出 |
| `sparse_vector` | 稀疏向量 | 用于关键词、命名实体、错误码召回 |
| `keywords` | 关键词 | 强化过滤和召回解释 |
| `language` | 语言 | 中文、英文或混合语料 |
| `source_type` | 来源类型 | 内部文档、案例库、面试题库、复盘库等 |
| `source_trust` | 来源可信度 | 官方、准官方、内部、历史材料等 |
| `freshness_score` | 时效分 | 体现内容是否需要优先召回 |
| `version_tag` | 版本号 | 文档或知识版本 |
| `embedding_model` | 向量模型 | 记录使用的模型名称 |
| `embedding_version` | 向量版本 | 用于灰度和回滚 |
| `security_level` | 安全等级 | 控制是否允许进入检索结果 |
| `created_at` | 创建时间 | 审计字段 |
| `updated_at` | 更新时间 | 版本治理字段 |

### 6.3 分区策略

对于这类有明确岗位分类的知识库，分区是非常有效的。

建议采用“岗位分区 + 通用分区”的混合方式：

- `common_core`：通用能力、通用方法论、跨岗位知识。
- `data_engineer`：数据工程师岗位知识。
- `devops`：开发运维岗位知识。
- `golang_backend`：Go 后端岗位知识。
- `java_backend`：Java 后端岗位知识。
- `machine_learning_engineer`：机器学习工程师岗位知识。
- `python_backend`：Python 后端岗位知识。
- `site_reliability_engineer`：SRE 岗位知识。
- `software_test_engineer`：测试工程师岗位知识。
- `system_architect`：系统架构师岗位知识。
- `web_frontend`：前端岗位知识。

如果一篇内容横跨多个岗位，建议优先通过 `role_tags` 表达，而不是重复写入多个分区。只有在极端追求检索效率时，才考虑多分区冗余。

### 6.4 索引策略

Milvus 对向量字段、稀疏字段和标量字段都能做索引。对于本方案，建议使用“主向量索引 + 辅助稀疏索引 + 标量过滤”的组合。

| 索引对象 | 推荐策略 | 适用场景 |
| --- | --- | --- |
| 稠密向量 | `AUTOINDEX` / `HNSW` / `IVF_*` / `DiskANN` | 语义召回主通道 |
| 稀疏向量 | 稀疏倒排或全文检索通道 | 命名实体、错误码、配置项、命令字串 |
| 标量字段 | 倒排、位图、分区过滤 | 岗位、类型、版本、时效、安全等级 |

选择建议如下：

- 如果知识库规模中等、召回质量优先，优先 HNSW 或自动索引。
- 如果数据量大、内存压力明显，优先 IVF 系列或 DiskANN。
- 如果内容更新频繁且日志/案例较多，保留稀疏通道会更稳。
- 如果要保证跨岗位共享能力，建议把通用知识与岗位知识分开治理。

### 6.5 余弦、内积与距离选择

Gemini Embedding 2 的向量可用于余弦相似度、内积或欧氏距离。对于面试场景，建议对外统一使用“语义相似度”作为业务表达，在底层实现上则依据引擎能力和向量归一化方式选择最合适的距离指标。

工程上最重要的不是“用哪种距离名词”，而是确保：

- 文档向量与查询向量来自同一模型版本。
- 向量归一化规则前后一致。
- 评分与重排逻辑在不同岗位间保持可比性。

## 7. 检索策略设计

### 7.1 检索不是单次相似度搜索

一个高质量的 RAG 检索过程，至少应该包含六步：

1. 问题理解。
2. 岗位路由。
3. 多通道召回。
4. 结果融合。
5. 重排与裁剪。
6. 上下文拼装与生成。

如果只做“向量近邻搜索 + 取前几条”，很容易在技术类问题上命中泛化内容，却错过真正关键的证据。

### 7.2 问题理解与岗位路由

第一步不是检索，而是判断问题属于哪个岗位、哪个子域、哪个问题类型。

例如：

- “Kubernetes 灰度发布失败怎么排查” 应路由到 `devops`，并联动 `site_reliability_engineer`。
- “Java 服务频繁 Full GC 怎么办” 应路由到 `java_backend`，并联动 `system_architect`。
- “如何设计实时特征工程与在线推理链路” 应路由到 `machine_learning_engineer`，并联动 `data_engineer`。

路由结果不一定只有一个岗位。很多高质量问题本身就是跨岗位问题，检索系统应该允许多岗位并行召回。

### 7.3 多通道召回

建议同时打开三条召回通道：

#### 语义召回

适合回答“是什么、为什么、怎么权衡”的问题。

典型问题：

- 架构设计怎么分层。
- 某个技术方案的优缺点是什么。
- 为什么要选某种方案而不是另一种方案。

#### 关键词召回

适合回答“具体名字、具体命令、具体错误、具体配置”的问题。

典型问题：

- 某个错误码怎么处理。
- 某个命令行参数的含义。
- 某个框架类名、方法名、配置键的用法。

#### 元数据过滤召回

适合缩小范围，提高精度。

典型过滤条件：

- `role_code`。
- `doc_type`。
- `version_tag`。
- `source_type`。
- `security_level`。
- `language`。
- `freshness_score`。

### 7.4 结果融合

召回结果出来后，不要直接按一个相似度分数排序就结束。建议使用融合策略把多个通道的结果整合起来。

可采用的融合逻辑包括：

- 统一加权。
- Reciprocal Rank Fusion。
- 语义分与关键词分分层融合。

高端场景下，建议把“语义分”“关键词命中”“岗位匹配”“来源可信度”“时效分”都纳入融合过程，而不是只看向量距离。

### 7.5 重排策略

重排阶段的目标是把“看起来像”与“真正有用”区分开来。

重排时建议考虑以下信号：

- 与当前岗位的匹配度。
- 与当前问题意图的匹配度。
- 是否包含明确证据、步骤或案例。
- 文档是否过期。
- 来源是否可信。
- 是否重复表达同一观点。

如果要做高质量回答，重排是必不可少的一步。尤其在系统架构、SRE、DevOps 和机器学习工程这类场景里，重排往往比单纯扩大 topK 更有效。

### 7.6 上下文拼装

最终给大模型的上下文，不应是“召回多少就塞多少”，而应是“按证据价值组装最小必要上下文”。

建议上下文拼装遵守以下原则：

- 保留标题、章节路径和来源。
- 一条证据只表达一个核心事实。
- 同质片段不要重复出现。
- 通用证据与岗位证据分层放入。
- 关键信息优先保留原文，次要信息可以摘要化。

### 7.7 查询改写

在进入 Milvus 之前，建议先做查询改写：

- 把口语化问题改写成知识检索问题。
- 把简称扩展成全称。
- 把中文表达中的技术词映射到英文术语。
- 把多问句拆成多个子查询。

例如：

- “微服务卡顿怎么排查” 可以扩展为“微服务性能下降、链路延迟、下游超时、缓存命中率、数据库慢查询”。
- “前端首屏慢” 可以扩展为“首屏渲染、资源拆包、懒加载、缓存、网络瀑布图、CLS/LCP”。

### 7.8 角色邻接检索

有些问题本身是跨岗位的，建议引入岗位邻接关系做扩展召回：

- `data_engineer` 可联动 `machine_learning_engineer` 和 `devops`。
- `golang_backend` 与 `java_backend` 都可联动 `site_reliability_engineer` 和 `system_architect`。
- `python_backend` 常常与 `machine_learning_engineer`、`software_test_engineer` 发生交叉。
- `web_frontend` 与 `software_test_engineer`、`system_architect` 的交叉频率也很高。

这种邻接召回能明显提升复杂问题的覆盖率，尤其在系统设计、工程落地和质量治理类问题上效果更好。

### 8.1 岗位策略说明

#### 数据工程师

这类问题经常带有强流程性和强术语性，因此检索时应同时保留数据管道术语、数据口径、指标定义和调度任务信息。数据工程师的检索不是单纯看“数据”两个字，而是要命中“血缘、延迟、口径、治理、重跑、补数、去重、分区、拉链、维表”等关键知识。

#### 开发运维

DevOps 场景中，最新知识往往比旧概念更重要，因此应显著提高时效权重。遇到发布失败、容器异常、服务抖动、配置漂移、权限问题时，应优先召回 runbook、变更记录、事故复盘和告警策略。

#### Go / Java / Python 后端

三个后端岗位共通点很强，但风格不同。Go 偏并发和性能，Java 偏生态和中间件，Python 偏工程效率和集成。检索系统应共享通用后端知识层，但在路由上保留岗位细分，以免把同一类问题召回成错误的语言答案。

#### 机器学习工程师

机器学习工程师的知识结构是多层的：数据、训练、评估、部署、推理、监控。检索时不能只看模型本身，还要把数据准备、实验管理、上线治理、模型漂移和 RAG 组件一起考虑进去。

#### SRE

SRE 的知识高度依赖真实事件与治理经验，因此事故复盘、值班手册、SLO 文档、容量评估和告警策略的权重应明显高于抽象定义。

#### 测试工程师

测试工程师的知识检索要兼顾测试方法论和实操细节。很多高质量答案来自测试分层、覆盖策略、稳定性治理、用例设计和缺陷分析，而不只是“自动化工具的名字”。

#### 系统架构师

架构师问题更像是“权衡问题”而不是“记忆问题”。因此系统架构师检索应优先稳定原则、决策记录和架构演进，而不是最新的工具碎片。

#### Web 前端工程师

前端知识既有工程性也有体验性。检索时应同时照顾渲染、状态管理、构建链路、可访问性和组件设计系统，避免只召回业务页面代码片段。

## 9. 文档入库与更新流程

建议把知识库建设成一条稳定的数据工程流水线，而不是一次性导入。

### 9.1 数据来源

可入库的内容建议包括：

- 岗位知识文档。
- 技术规范与设计文档。
- 面试题与参考答案。
- 故障复盘与事件报告。
- 项目案例与架构决策记录。
- 测试规范与质量标准。
- 运行手册与发布手册。

### 9.2 清洗标准

入库前应统一完成：

- 结构清洗：去掉目录噪音、重复页眉页脚、无效装饰。
- 语义清洗：合并过短断句，拆分过长混杂段落。
- 标签清洗：统一岗位编码、文档类型和版本号。
- 安全清洗：剔除敏感信息或进行脱敏。

### 9.3 质量门禁

一条知识能否入库，不应只看“有没有文本”，还要看：

- 是否可追溯。
- 是否可分类。
- 是否可复用。
- 是否过期。
- 是否与岗位关联明确。

### 9.4 增量更新

建议采用增量更新，而不是频繁全量重建。

- 高频更新内容：runbook、故障复盘、规范修订。
- 中频更新内容：题库、案例、岗位指南。
- 低频更新内容：方法论、架构原则、评价标准。

### 9.5 失效与回滚

过期知识不能简单删除，建议先标记失效，再根据效果决定是否真正下线。这样可以保留审计能力，也方便回滚。

## 10. 质量评估与可观测性

### 10.1 检索质量指标

建议重点监控以下指标：

- Recall@K：给定问题时，正确证据是否进入候选集。
- MRR：正确证据是否排在前列。
- nDCG：排序质量是否稳定。
- Coverage：不同岗位是否都能被覆盖。
- Freshness Hit Rate：最新知识是否能被优先召回。
- Source Coverage：证据来源是否多样且可信。

### 10.2 生成质量指标

RAG 最终不是为了检索本身，而是为了生成可用答案，因此还要评估：

- Faithfulness：生成内容是否忠于证据。
- Grounding Rate：答案是否被检索证据支撑。
- Citation Completeness：引用是否完整。
- Hallucination Rate：是否出现无依据回答。
- Role Accuracy：答案是否符合目标岗位。

### 10.3 运行指标

在工程运行上，还要关注：

- 端到端检索延迟。
- 向量查询耗时。
- 标量过滤耗时。
- 重排耗时。
- 索引构建时间。
- 增量更新滞后时间。
- 缓存命中率。
- 召回失败率。

### 10.4 黄金问题集

建议为每个岗位准备一组“黄金问题集”，并定期回归验证。例如：

- 数据工程师：数据口径、链路延迟、ETL 容错、血缘追踪。
- DevOps：发布回滚、K8s 排障、CI/CD、监控告警。
- Go 后端：并发控制、性能分析、接口治理。
- Java 后端：JVM 调优、事务、一致性、缓存。
- 机器学习工程师：训练评估、模型部署、RAG、数据漂移。
- Python 后端：异步、测试、API 设计。
- SRE：事故处理、SLO、容量、应急预案。
- 测试工程师：策略设计、自动化、回归与缺陷。
- 系统架构师：架构决策、扩展性、标准化。
- 前端：性能优化、组件设计、体验与可访问性。

## 11. 安全、权限与治理

RAG 知识库一旦进入企业级应用，就不能只考虑“能不能搜到”，还要考虑“该不该搜到”。

### 11.1 权限隔离

建议按以下维度做访问控制：

- 岗位级访问。
- 项目级访问。
- 安全等级访问。
- 环境级访问。

### 11.2 敏感信息治理

所有入库内容都应避免包含：

- 明文密钥。
- 个人隐私。
- 客户敏感数据。
- 未授权的内部信息。

必要时应做脱敏、模糊化或摘要化处理。

### 11.3 审计与追踪

每条知识都应能追踪到：

- 来源。
- 版本。
- 作者或维护者。
- 生效时间。
- 失效时间。
- 审批记录。

这会显著提升后续排障、复盘和治理效率。

## 12. 分阶段落地建议

### 12.1 第一阶段：单库单向量

目标是快速上线、验证业务价值。

- 使用单个主集合。
- 只保留 dense vector。
- 以 `role_code` 和 `doc_type` 做过滤。
- 先打通入库、召回、生成闭环。

适合快速验证“这个岗位有没有答案、答案是不是靠谱”。

### 12.2 第二阶段：混合检索

目标是显著提升精确命中率。

- 增加 sparse / full-text 通道。
- 引入 RRF 或加权融合。
- 对 DevOps、SRE、测试、后端等术语密集岗位进行优化。
- 为角色路由加入邻接扩展。

适合把“像答案”提升到“更像对的答案”。

### 12.3 第三阶段：分层治理

目标是让知识库具备长期演化能力。

- 通用层与岗位层分开治理。
- 版本化管理 embedding 与文档。
- 热知识与冷知识分层存储。
- 建立黄金问题集和自动回归。

适合规模化运营和持续迭代。

## 13. 推荐的检索编排模式

下面是本方案推荐的“高质量检索编排”逻辑：

1. 先识别问题对应的岗位或岗位组合。
2. 再做查询改写，把口语化表达转成知识化表达。
3. 用岗位分区和标量过滤缩小范围。
4. 并行执行语义召回与关键词召回。
5. 用融合策略汇总候选集。
6. 用重排模型或规则对候选集再次排序。
7. 按证据价值裁剪上下文，交给生成模型。
8. 生成后保留来源信息，便于解释和追踪。

如果要把这个流程压缩成一句话，就是：

**先路由，再召回；先融合，再重排；先证据，后生成。**

## 14. 方案结论

Gemini Embedding 2 + Milvus 的组合，适合构建一个既能覆盖十个岗位、又能承载持续演化的企业级 RAG 知识底座。它的关键不在于“向量库本身”，而在于是否把岗位路由、知识分层、混合检索、版本治理和质量评估真正做完整。

如果只把它当作一个“搜文档”的工具，效果通常不会稳定；如果把它当作一个“岗位知识操作系统”，那么它就能同时支撑面试问答、题目生成、追问建议、复盘辅助和知识治理。

这套方案的目标，就是让检索结果不仅“搜得到”，还要“搜得准、搜得快、搜得可解释、搜得可持续”。
