# 人工智能面试模拟器 1.0 项目文档

> 版本定位：接口编排版面试系统，采用 FastAPI + REST + SSE 的方式驱动面试流程。
> 核心特点：后端主导流程、模型负责内容生成、回调负责结果闭环。

本文是 1.0 的正式项目文档，目标不是单纯描述接口，而是从架构、设计原则、数据契约、流程治理、部署与运维等角度，完整说明这个版本的设计方式与工程实践。

## 1. 项目目标

1.0 的目标是把一次技术面试抽象成一条稳定、可控、可审计的服务链路。

- 前端或后端显式调用 `start`、`followup`、`analysis`、`report`。
- 所有面试阶段由服务端状态和流控策略决定，不把流程控制交给模型自由发挥。
- 支持流式输出，兼顾实时展示和后端控制。
- 最终报告独立生成，并通过回调送达业务系统。

> PPT 版一句话定位：1.0 不是“聊天接口”，而是一套以流程编排、结构化评分和结果回调为核心的面试工作流引擎。
>
> 配图建议：这里最适合放一张总览架构图，展示“请求输入 -> 服务端裁决 -> 模型生成 -> 评分 -> 回调闭环”的主路径。

这个设计更适合对流程、幂等和审计要求高的场景，例如企业内部面试系统、岗位筛选系统和带回放能力的评估系统。

## 2. 设计原则

### 2.1 契约优先

所有请求和响应都通过 Pydantic schema 定义，减少跨团队联调时的字段歧义。

### 2.2 后端裁决

`followup` 的阶段推进不是完全由模型决定，而是由服务端根据历史记录、难度策略和低质量回答策略做裁决。

### 2.3 长上下文治理

引擎会对历史摘要、问题、回答和报告结果做截断，避免 prompt 无限膨胀。

### 2.4 可回放与可审计

每次分析都会返回分维度评分，最终报告保留结构化评分细节，便于后续追踪与复盘。

### 2.5 失败可恢复

接口失败、模型失败、回调失败都要留下清晰日志，方便重试和排障。

## 3. 总体架构

### 3.1 代码组成

- `app/main.py`：FastAPI 路由、流式输出、报告异步派发、回调发送。
- `app/LLM_engine/engine.py`：模型接入、Prompt 渲染、JSON 修复、评分和报告生成。
- `app/schemas/schemas.py`：请求模型、评分模型、报告模型。
- `app/prompts/`：各阶段 Prompt 文件。
- `Dockerfile`：1.0 容器入口。

> 配图建议：这一节适合配一张“模块分层图”，把 API、LLM 引擎、Schema、Prompt、部署入口画成左右或上下分层。

### 3.2 运行模式

1. 接口收到请求后由 `LLMEngine` 调用 `AsyncOpenAI`。
2. 通过 Prompt 模板把岗位、简历、历史轮次和阶段信息拼成模型输入。
3. 模型返回 JSON 或类 JSON 文本后，服务端用 `json_repair` 做修复。
4. 评分与报告在代码层做二次标准化。
5. 报告通过固定回调地址送达业务系统。

> 说明：1.0 的 ml-service 主链路只处理文本输入。若业务上游有音频，语音转文字需要由外部后端先完成，再把 transcript 调用到 1.0 的接口里。

### 3.3 依赖与技术栈

- Web 框架：FastAPI
- 流式响应：SSE
- 模型接入：OpenAI 兼容客户端
- JSON 修复：`json-repair`
- 模板渲染：Jinja2
- 数据约束：Pydantic
- 部署：Docker、uvicorn

## 4. 目录结构与职责边界

### 4.1 服务端主流程

`app/main.py` 负责三类事情：

- 对外暴露 API。
- 根据难度和轮次做流控。
- 将最终报告发送到回调地址。

### 4.2 模型引擎

`app/LLM_engine/engine.py` 负责四类事情：

- 读取 Prompt 配置。
- 构造系统提示词和用户提示词。
- 发起模型调用并解析结果。
- 把分维度分数和总分标准化。

### 4.3 数据模型

`app/schemas/schemas.py` 定义了以下关键契约：

- `StartRequest`
- `FollowupRequest`
- `AnalysisRequest`
- `ReportRequest`
- `InterviewConfig`
- `FlowControl`
- `DimensionScores`
- `DimensionDetails`
- `RoundResultItem`

## 5. 核心流程

### 5.1 开始面试

`POST /api/v1/interview/start` 用于生成首轮问题。

输入：岗位、JD、简历、面试配置、阶段控制。

输出：首轮问题和阶段流控结果。

### 5.2 追问阶段

`POST /api/v1/interview/followup` 用于根据历史轮次生成下一问。

服务端会结合以下信息做裁决：

- 当前阶段
- 最近轮次
- 难度策略
- 用户回答是否过短
- 用户是否表达“没有更多问题”

#### 阶段策略

当前阶段序列为：

`intro -> resume_deep_dive -> tech_general -> tech_scenario -> reverse_qa -> end`

服务端会根据轮次、阶段最小/最大次数和低质量回答阈值决定：

- 继续当前阶段
- 切换到下一阶段
- 直接结束

这体现了 1.0 的核心原则：流程裁决在后端，不交给模型任意决定。

### 5.3 单轮分析

`POST /api/v1/interview/analysis` 用于分析某一轮回答。

返回结构包含：

- `professional`
- `cognition`
- `expression`
- `dimension_scores`
- `final_score`
- `overall_feedback`
- `improvement_suggestions`

### 5.4 最终报告

`POST /api/v1/interview/report` 用于提交最终报告任务。

当前实现特点：

- 使用固定的 `REPORT_CALLBACK_URL_TEMPLATE`。
- `callback_url` 仅作为兼容字段保留。
- 回调体会发送最终报告对象本身，不再额外包一层业务响应结构。
- 报告内容来自引擎生成后再做标准化。

## 6. 数据契约与评分规则

### 6.1 面试配置

`InterviewConfig` 允许以下值：

- `mode`: `text | audio | video`
- `interviewer_style`: `standard | friendly | aggressive | expert`
- `difficulty`: `easy | medium | hard`
- `company_context`: 可选字符串

> 说明：虽然 Schema 里保留了 `audio` / `video` 字段以兼容上游传参，但当前 1.0 的实现不在 ml-service 内做音频采集、VAD 或 ASR，实际运行仍以文本链路为主。

### 6.2 阶段控制

`FlowControl` 只允许：

- `stage_transition`: `continue | switch | end`
- `target_stage`: `intro | resume_deep_dive | tech_general | tech_scenario | reverse_qa | end`

### 6.3 分数公式

当前系统采用的权重如下：

```text
professional = 0.20 * technical_correctness + 0.09 * knowledge_match + 0.31 * job_match + 0.40 * engineering_practice
cognition = (logic_structure + problem_solving + system_thinking) / 3
expression = (clarity + confidence_stability + professional_maturity) / 3
final_score = round((0.5 * professional + 0.3 * cognition + 0.2 * expression) * 20, 1)
```

这套公式的含义是：

- 专业能力权重最高。
- 认知能力体现结构化思考和问题拆解能力。
- 表达能力衡量沟通的稳定性和专业度。

### 6.4 报告结果结构

最终报告包含：

- `hiring_recommendation`
- `executive_summary`
- `strengths`
- `weaknesses`
- `ability_trend`
- `detailed_recommendation`
- `professional`
- `cognition`
- `expression`
- `dimension_scores`
- `overall_score`

其中 `dimension_scores` 和 `overall_score` 由服务端回算，不依赖模型自由发挥。

## 7. Prompt 设计思想

### 7.1 起始问题 Prompt

负责生成首轮开场问题，强调：

- 简洁
- 贴合岗位
- 不要一次性问太多

### 7.2 追问 Prompt

负责在历史上下文中生成下一问，并携带阶段信息、上一轮摘要和最近轮次。

### 7.3 评分 Prompt

负责分析单轮回答的技术准确性、岗位匹配度、逻辑结构和表达表现。

### 7.4 报告 Prompt

负责生成最终报告本体，不负责总分；总分由代码回算。

- 任何影响模型调用稳定性的参数都应该通过环境变量控制，而不是写死在代码里。

## 9. 创新点与优势

### 9.1 PPT 可直接引用的卖点

- 1.0 的核心价值不是“更会问问题”，而是“更可控、更可审计、更容易被业务系统接住”。
- 它把面试拆成标准化的四段式链路：起问、追问、分析、报告，天然适合企业级流程治理。
- 服务端掌握阶段裁决权，避免模型自由发挥带来的流程漂移。
- 评分和报告在代码层做二次标准化，便于统一口径、横向比较和长期复盘。
- 回调闭环让结果可以直接进入后端系统，不需要额外人工搬运。

### 9.2 适合强调的工程优势

- 契约优先：接口字段、评分结构、流程状态全部显式定义。
- 结果可追踪：每轮分析和最终报告都保留结构化证据。
- 易于集成：REST + SSE 形态对前后端和网关都友好。
- 易于治理：流控、日志、回调、重试都在后端可控范围内。
- 易于扩展：后续可以在不推翻现有流程的前提下接入更强的知识增强或实时智能体能力。

## 10. 部署方式

### 10.1 本地启动

```bash
cd ml-service
conda run -n ml-service uvicorn app.main:app --host 0.0.0.0 --port 8000
```

也可以直接执行：

```bash
cd ml-service
conda run -n ml-service python app/main.py
```

### 10.2 Docker 部署

```bash
cd ml-service
docker build -f Dockerfile -t ai-interview-1-runtime:latest .
docker run --rm -p 8000:8000 --env-file .env.ml-service ai-interview-1-runtime:latest
```

### 10.3 部署建议

- 1.0 是 HTTP 服务，适合挂在常规 API 网关后面。
- 报告回调地址应保持幂等。
- 对外接口要保留请求追踪和错误日志。

## 11. 可观测性与容错

### 11.1 日志

建议重点关注以下日志维度：

- 请求日志
- 响应日志
- 报告回调日志
- 模型调用失败日志
- JSON 修复失败日志

### 11.2 容错机制

- 模型返回非标准 JSON 时使用 `json-repair` 尝试修复。
- 回调失败时使用指数退避重试。
- 历史窗口和文本长度都做了裁剪，避免上下文失控。

### 11.3 幂等性

回调接收端应以 `session_id` 作为幂等主键，避免重复回调造成重复入库。

## 12. 测试与验收

### 12.1 建议验证点

- `start` 能返回首轮问题。
- `followup` 能根据历史轮次推进阶段。
- `analysis` 能返回维度分数和总分。
- `report` 能生成最终报告并回调。
- 回调地址中的 `interviewId` 和 `session_id` 保持一致。

### 12.2 验收建议

建议从以下三个维度验收：

1. 功能正确性：接口返回符合契约。
2. 稳定性：模型调用失败时有明确错误和重试。
3. 可维护性：日志、配置、Prompt、回调路径都便于排障。

## 13. 当前版本边界

1.0 的边界非常清晰：

- 适合流程强控。
- 适合接口联调。
- 适合需要回放和审计的场景。
- 不适合作为强实时语音对话引擎。

如果你的目标是更强的实时交互体验，应该参考 2.0 的实时运行时设计。

## 14. 总结

1.0 的本质，是一个以接口契约为中心、以后端裁决为核心、以报告回调闭环为终点的面试系统。
它的优势不在“更像真人”，而在“更可控、更稳定、更容易和业务系统对齐”。
